# Grill Review — Mail-Einstellungen & E-Mail-Versand (Infrastruktur)

- Target: `docs/forge/spec/2026-07-22-mail-settings.md`
- Date: 2026-07-22
- Reviewer: fresh adversarial reviewer, did **not** author this spec.

Scope: verified the load-bearing "Existing Architecture" claims against the repo. `SecurityFilter.java:96` default-deny is real, so new un-whitelisted `/mail-settings` paths are admin-only as R5 claims (no finding there). `OrganisationResource.java:22-63` GET returns `entries` generically, so D1's "tag reuse would leak the encrypted blob" rationale is factually supported — D1 stands. Findings below are about the design's security, failure, and testability gaps, plus one internal contradiction.

---

### [G-001] [Blocker] Dev-default encryption key contradicts the fail-closed rule and silently defeats R3
- **Section:** Assumptions (L77), Migration & Compatibility (L128), D3, R3
- **Finding:** Two statements collide. Assumptions L77: "Fehlt [der Schlüssel], ist Speichern/Versand deaktiviert und meldet einen klaren Fehler" — a fail-closed safety mechanism keyed on the config being *absent*. Migration L128: "`KIGRUAPP_MAIL_ENCRYPTION_KEY` … Dokumentation in `application.properties` (Default nur für dev)." If a default value ships in `application.properties`, the key is **never absent** — the fail-closed branch can never fire. Concrete failure: an operator deploys to production and forgets to override the env var. The app does not refuse to start or disable saving (the L77 promise); it silently encrypts SMTP passwords with a well-known, source-controlled key. R3 promises the password is "verschlüsselt at-rest" as a security guarantee. Against anyone with a DB dump *and* the repo (every developer, anyone with source access), that encryption provides zero confidentiality. The spec asserts both the safety net and the thing that removes it. This is damage-if-built-as-written: a false sense of at-rest protection with no failure signal.
- **Question the author must answer:** Does a default key ship in `application.properties`, or does a missing `KIGRUAPP_MAIL_ENCRYPTION_KEY` hard-disable save/send (fail closed) with no default — and if a dev default is kept, what prevents it from being the effective production key and how is that reconciled with R3?
- **Resolution:** Resolved: no default key ships anywhere (incl. dev); missing/invalid key hard-disables password-save and send (fail-closed) with a clear error. R3 extended, Assumptions + Migration updated.

### [G-002] [Major] AES-GCM key derivation and nonce generation are unspecified — a conforming implementation can be insecure
- **Section:** D3 (L64), Component Responsibilities (`EncryptionService`)
- **Finding:** D3 says only "AES-GCM … Schlüssel aus Konfiguration" and "Gespeichert wird base64(iv‖ciphertext)." Two security-critical parameters are left to the implementer: (a) how the config string becomes an AES key — raw `getBytes()` (wrong length → `InvalidKeyException` or silent truncation; a short passphrase yields a weak key), base64-decoded 32 bytes, or KDF-derived (PBKDF2/HKDF with salt)? (b) how the 12-byte GCM nonce/IV is produced. AES-GCM is catastrophic under nonce reuse with the same key: two ciphertexts under a reused nonce leak plaintext XOR and, worse, allow authentication-tag forgery. The spec does not require a `SecureRandom` per-encryption nonce. A literal implementation that derives the key from `secret.getBytes()` and uses a fixed or counter IV would "conform" to D3 and be broken. Nothing in R1–R9 constrains this, so it is untestable from the requirements.
- **Question the author must answer:** What is the exact key material contract (encoding, required length, whether a KDF+salt is used) and what guarantees a unique per-encryption nonce?
- **Resolution:** Resolved: new R10 fixes key = base64-encoded 32 bytes (AES-256), validated at startup; 12-byte SecureRandom nonce per encryption; stored as base64(iv‖ciphertext‖tag). D3 spelled out.

### [G-003] [Major] No key-rotation path — deliberate rotation is silent total credential loss
- **Section:** Risks (L155), D3, Migration & Compatibility
- **Finding:** The Risks section addresses key *loss* ("Admin muss es neu eingeben"). It never addresses deliberate key *rotation*, which is a routine security practice (secret rotation policies, compromised-key response, staff turnover). Because the ciphertext carries no key identifier/version and there is no re-encrypt migration, rotating `KIGRUAPP_MAIL_ENCRYPTION_KEY` has the exact same effect as losing it: every stored password becomes undecryptable at once, `MailService` starts failing on decrypt, and the only recovery is manual re-entry — with no detection until a send fails. Treating "loss" and "rotation" as the same unhandled event understates a one-way-door property of the storage format: the format is welded to a single, unversioned, never-changeable key.
- **Question the author must answer:** How does an operator rotate the encryption key without breaking every stored password — key versioning in the stored blob and a re-encrypt step, or is rotation explicitly declared unsupported and documented as "re-enter password after any key change"?
- **Resolution:** Resolved: rotation explicitly unsupported (no key versioning — avoids speculative complexity); after any key change/loss decrypt fails closed and the admin re-enters the password. Documented in D3, Risks, Migration, Non-Goals.

### [G-004] [Major] Synchronous send with unspecified (default-infinite) timeouts can pin worker threads
- **Section:** Risks (L157), Performance (L139), Assumptions (L81), Data Flow (test/send)
- **Finding:** Send is synchronous in the request thread (Assumption L81). The blocking risk is named (L157) with the mitigation "Connection-/Timeout-Properties … setzen" — but no concrete values, and it is only a Risk note, not a requirement (no R covers it). `jakarta.mail`'s `mail.smtp.connectiontimeout` and `mail.smtp.timeout` default to **infinite**. If the implementer omits them (the spec does not force otherwise), a slow, firewalled, or black-holing SMTP host hangs the Quarkus worker thread until an OS-level TCP timeout or forever. This is directly reachable: the test endpoint (D4) lets an admin trigger a connection to an arbitrary host:port (see also G-008 SSRF), so an admin — or a mistyped host — can tie up threads. Enough concurrent hung sends exhaust the worker pool and degrade the whole app, not just mail.
- **Question the author must answer:** What are the concrete connect/read timeout values, are they a hard requirement (testable) rather than a hopeful risk note, and does anything cap concurrent in-flight sends?
- **Resolution:** Resolved: new R11 makes connect- and read-timeout = 10s each a hard requirement. No concurrency cap in scope (single-admin; only the testmail trigger exists) — deliberately deferred to the first bulk-send feature; documented in Performance + Non-Goals.

### [G-005] [Major] Dropping quarkus-mailer removes the test seam; R6/R7 delivery is left effectively untestable, and D2's rejection is a partial strawman
- **Section:** D2 (L58-59), Alternatives Considered (L148), R6, R7, Success Criteria
- **Finding:** D2 rejects `quarkus-mailer` solely as "an Startup/`application.properties` gebunden." That is the strongest version of the argument for the injected reactive `Mailer`, but it omits what quarkus-mailer buys: a `MockMailbox` test double and dev-mode mail capture, plus the option of constructing a mailer programmatically. By choosing raw `jakarta.mail` and building a `Session` by hand, the design leaves R6 ("echte E-Mail im Zielpostfach") and R7 (`MailService.send`) with **no specified test double**. Success Criteria confirm this: verification is described as a real mailbox delivery — a manual/integration step needing a live SMTP or a GreenMail-type fake that the spec never introduces. So the two core behaviors of an "infrastructure" spec have the weakest automated testability, and the decision that caused it did not weigh the testing cost of what it discarded.
- **Question the author must answer:** How are `MailService.send` (R7) and the testmail (R6) verified in the automated suite without quarkus-mailer's mock — is a fake SMTP server (e.g. GreenMail) an accepted new test dependency, and if so why does it not appear in the spec's dependency/constraint set?
- **Resolution:** Resolved: GreenMail added as accepted test-only dependency for automated R6/R7 verification; MailService's session/connection build kept isolable. Added to Constraints, D2, Success Criteria, Alternatives. D2 (runtime DB config) stands.

### [G-006] [Major] "Infrastructure only" with no first consumer makes the MailService contract speculative and one-way
- **Section:** Goal (L9), R7, Assumptions (L79), Non Goals, Interfaces (L100)
- **Finding:** The spec is explicitly scoped to infrastructure with "konkrete fachliche Versand-Anwendungsfälle … nicht Teil dieser Spec." R7 defines `MailService.send(recipient: String, subject: String, body: String)` as "der Einstiegspunkt für spätere fachliche Versand-Features" — an internal API frozen with zero real callers. The shared engineering rules (rules.md L115, "Nothing speculative") caution against exactly this. The chosen signature bakes in single recipient, no CC/BCC, plaintext-only body (Assumption L79) — the first real consumer (welcome mails, group notifications named in Non Goals) will plausibly need multiple recipients, per-locale bodies, or HTML, forcing a signature change and re-touching the one place the spec calls the "central entry point." Without a concrete first use case, there is no evidence this contract survives contact with a real feature, yet it is presented as the stable seam everything later hangs off.
- **Question the author must answer:** What is the minimal concrete first consumer that justifies this exact signature now, or should `MailService` be introduced together with that first feature so its contract is shaped by a real caller rather than guessed?
- **Resolution:** Resolved: infra+testmail scope is a confirmed user decision; the testmail endpoint is the concrete first consumer justifying send(recipient,subject,body). Contract marked explicitly provisional/internal with no stability guarantee (R7, Risks).

### [G-007] [Major] Empty-password-means-unchanged leaves no way to clear a credential, and "incomplete" is undefined for auth-optional SMTP
- **Section:** R4, D5, R8, Interfaces (PUT), Data Flow
- **Finding:** R4/D5 fix "leeres Passwortfeld = unverändert." This has no inverse: once a password is stored, there is no described operation to *remove* it. Concrete cases: an admin switches to an unauthenticated internal relay (no username/password), or a wrong password was saved and the admin wants to blank it — both are impossible through the only PUT semantics given (empty = keep old). Separately, R8 refuses send when settings are "unvollständig" but never defines completeness for the legitimate no-auth case: with `encryption=NONE` and an open relay, username and password are optional, yet a naive "all fields required" completeness check would wrongly block it, or a naive "password required" check would wrongly demand one. The two rules interact badly and neither pins down the auth-optional path.
- **Question the author must answer:** What UI/API action clears a stored password (an explicit "remove password" control, or a sentinel), and precisely which fields make settings "complete" when the target SMTP server requires no authentication?
- **Resolution:** Resolved: explicit `clearPassword` flag in PUT removes a stored password (R4). Completeness (R8) = host+port+encryption+fromAddress; username optional; if username is set but no password was ever stored, config is incomplete.

### [G-008] [Minor] Test endpoint's always-200 contradicts the missing-key 500 path and turns error messages into an SSRF/info oracle
- **Section:** Error Handling (L120, L123), Security Considerations (L133, L135), R6, D4
- **Finding:** Error Handling L123 says the test endpoint returns `200 {success:false}` on failure "damit die UI die Meldung einfach anzeigt," but L120 says a missing encryption key returns "500/Fehler." These collide for the realistic case of a *test send while the key is missing/invalid*: 200-with-message or 500? Undefined. Two further tensions: (a) `{success:false, message}` conflates config errors, SMTP auth failures, and network failures into one string, so R6's "konkrete Fehlermeldung" and the UI's handling are underspecified. (b) Returning the raw SMTP/connection error as `message` (L122 promises "sprechende message") to an admin who can aim the test at any host:port makes the endpoint a probe: connection-refused vs. timeout vs. TLS banner distinguishes live internal hosts and services — an SSRF confirmation/port-scan oracle — which sits in tension with Security L135 "SMTP-Fehlermeldungen ohne Credentials" (that only forbids creds, not banners).
- **Question the author must answer:** For a test send with a missing/invalid key, is the response 200-with-message or 500 — and are raw upstream connection/SMTP messages surfaced verbatim to the admin, or normalized to a fixed set to avoid the internal-host probe?
- **Resolution:** Resolved: test endpoint returns 200 for all operational outcomes incl. missing key (category CONFIG_MISSING); 500 only for unexpected errors. Response uses a fixed category set {OK,CONFIG_MISSING,AUTH_FAILED,CONNECTION_FAILED,UNKNOWN} + normalized message, never raw SMTP banners. Error Handling, Interfaces, Security updated.

### [G-009] [Minor] Singleton identity and concurrent upsert are unspecified
- **Section:** D1, Component Responsibilities (`MailSettings`), Data Flow (upsert)
- **Finding:** `MailSettings` is described as a "Singleton-Dokument" saved via "Upsert," but the mechanism that enforces singularity is never stated — fixed well-known `_id`, a `findFirst`-then-update, or a unique index. Without a fixed identity, two overlapping PUTs (or a save racing an empty initial GET) can insert two documents, after which "the" settings become non-deterministic. Risk is low at single-admin scale, but the spec markets the singleton as a design property while omitting what makes it one.
- **Question the author must answer:** How is singleton identity enforced — a constant `_id`/upsert filter or a unique index — so concurrent saves cannot create a second `mail_settings` document?
- **Resolution:** Resolved: enforced via a constant well-known `_id` used as the fixed upsert filter, so concurrent PUTs hit the same document. Component Responsibilities updated.

### [G-010] [Minor] SMTP transport trust is unspecified — credentials interceptable via missing identity check / STARTTLS downgrade
- **Section:** D3, Security Considerations, Data Flow (L114 "baut jakarta.mail-Session gemäß encryption")
- **Finding:** The design decrypts the password to plaintext and hands it to a hand-built `jakarta.mail` session, but says nothing about transport certificate validation. `jakarta.mail` defaults `mail.smtp.ssl.checkserveridentity` to **false**, so even with SSL/TLS or STARTTLS selected, the client does not verify the server hostname against its certificate — a network MITM can present any cert and harvest the SMTP username/password. STARTTLS additionally is downgrade-susceptible unless `mail.smtp.starttls.required` is set. The spec encrypts the password at rest (G-001/G-002) but is silent on protecting it in transit, which is where it is actually exposed on every send.
- **Question the author must answer:** Will the session enforce `checkserveridentity=true` and `starttls.required=true` (for the STARTTLS mode) so decrypted credentials are not exposed to a MITM, and is that a testable requirement?
- **Resolution:** Resolved: new R12 makes checkserveridentity=true always, plus starttls.enable+required in STARTTLS mode, a testable requirement. D3 and Security updated.

## Attack vectors checked, nothing material
- **Existing-architecture accuracy:** Verified SecurityFilter default-deny (`:96`) and OrganisationResource generic GET (`:22-63`). Both claims hold; R5's admin-only-by-default mechanism is sound and D1's leak rationale is real. No finding.
- **Migration/backfill:** Greenfield new collection, empty defaults, no data migration. Clean (the only migration risk is the encryption-key handling — covered by G-001/G-003).
- **Scale/load:** Correctly identified as trivial (rare admin config, no batch). Agree — the real thread risk is timeout, not throughput (G-004).
- **Authz on new endpoints:** Confirmed no whitelist entry is needed; default-deny covers `/mail-settings/**`. Matches the spec.
- **R1/R2/R3/R4/R5/R8/R9 testability:** Individually testable (persistence-survives-restart, DTO-omits-password, empty-preserves, non-admin-403, fail-closed-when-disabled, field validation). The weak spots are R6/R7 delivery (G-005) and the crypto/timeout/transport requirements that are not stated as requirements at all (G-002/G-004/G-010).
